# Etyma 1.0 readiness

## What 1.0 means

1.0 is a stability promise, not a feature milestone. Every export, generated artifact,
diagnostic code and CLI exit code that exists at 1.0 keeps working, with the same meaning,
for every 1.x release - and Etyma does not become 1.0 until the authors are willing to make
that promise about what is there. Adding a capability is a minor release; anything listed
below as post-1.0 can arrive in one without a 2.0.

## Hard gates

- [x] **Deliberate public exports.** Every package's entry points are asserted exactly by
      `pnpm package:check`; `@etyma/cli` is a binary with no importable entry point. Each
      README separates the application API from the advanced adapter/tooling API.
- [x] **Stable `MessageContract` shape.** `defineMessageContract({ keys, variables?,
functions? })`: one object whose fields match the `MessageContract` it returns, so new
      metadata is a new optional field. Unknown fields are ignored at runtime and are a
      compile error, which names the field when a newer generator meets an older core.
- [x] **Stable diagnostics.** Codes are namespaced and never carry dynamic values; ordering is
      by code unit, independent of the host locale. Codes are never renamed, removed or
      re-graded within a major; minors may add codes.
- [x] **Stable CLI exit semantics.** `0` success, `1` validation failure or stale contract
      (`--check`), `2` usage, configuration, filesystem, network or generation failure - the
      same in the implementation, `--help` and the README for every command.
- [x] **Framework matrix verified against packed tarballs.** Angular 21/22, Analog 2.6/2.7,
      Astro 6/7, and a framework-free `@etyma/core` consumer (`pnpm compat:check`).
- [x] **SSR and request isolation.** Per-request registries in Angular, per-render state in
      Astro with a prerender-only catalog cache, concurrent SSR requests in e2e, and multiple
      definitions in one process - all covered by tests.
- [x] **Type performance at application scale.** `tools/compat/core-large-catalog` types an
      836-key generated catalog - nested namespaces, arrays, zero to three params, numeric,
      currency, plural and date/time annotations - through a literal source, a JSON source
      with a contract, a literal source with a contract, and a remote definition, against
      the packed `@etyma/core`, with bounded declaration output.
- [x] **Reliable release pipeline.** Changesets release PR, automatic publish with every gate
      re-run, npm provenance.
- [x] **Docs match behaviour.** Package READMEs and the root README are current, and the
      official site's copy describes nothing this release changed. Its brand sub-label
      (`layout.status`) is version-neutral ("typed i18n"), so a release cannot make it stale.
- [x] **Dogfood on the current API without architecture changes.** Internal and external; see
      [Dogfood evidence](#dogfood-evidence) below. Result: pass, with application fixes only.

## Release scope

The first stable milestone covers **all six public packages**: `@etyma/core`,
`@etyma/angular`, `@etyma/analog`, `@etyma/astro`, `@etyma/tooling` and `@etyma/cli`. One
`major` changeset takes each from `0.x` to `1.0.0`. Their version groups do not change
afterwards - the runtime trio stays fixed together, the other three version independently
([RELEASING.md](RELEASING.md)). No official package is left behind at `0.x`: each one's
documented surface passed the same audit, and a split ("core is 1.0, tooling is not") would
make the promise harder to state, not safer to keep.

The promise covers documented public exports, documented generated formats (the contract
module), diagnostic codes and their severity meaning, and CLI commands, options, output and
exit semantics. It does not cover private files, internal syntax-tree representations,
caches, helper names, algorithms or test fixture layout; message _wording_ in diagnostics may
change in a minor release.

Status of this record: all gates are met and the 1.0 changeset is in the repository. Nothing
is published until the generated **release: version packages** PR is merged.

## Dogfood evidence

External dogfood: **PASS WITH APPLICATION FIXES.** Etyma's strict types exposed consumer
mistakes; they are positive evidence, not Etyma regressions, and no Etyma API or architecture
change was needed.

- **`Andersseen/my-blog`** - Astro 6, remote catalogs, `@etyma/core`/`tooling` `^0.5.0` and
  `@etyma/astro` `^0.2.2`, from published npm packages (PR #16, merged as `5f152f9`). Exercised
  the one-object `defineMessageContract`, generated variable/function metadata, typed
  parameter names and values, the Astro integration and remote contracts. Application fixes:
  an explicit `AstroI18n<MessageKey>` annotation erased the `TParams` generic (inference was
  preserved instead), and overly broad `MessageKey` metadata made arbitrary runtime keys
  require the union-safe params (the metadata types were narrowed).
- **`Andersseen/volt-ui`** - Angular + Analog, remote catalogs, `@etyma/core`, `angular`,
  `analog` and `tooling` `0.5.0` (PR #141, merged as `3b9c602`). A 766-key generated
  contract with variable metadata and `:number` annotations, typed names and values, real
  `ngc` template checking, and hydration/e2e. Application fixes: a `EtymaI18n<TranslationKey>`
  return annotation that erased `TParams` was removed, static metadata was narrowed to
  non-param keys, one parameterized message moved out of an overly broad component API,
  `ngc` template checking was enabled, and a stale Etyma hydration `test.fail` was removed.

Releases since the hardened 0.5 API do not invalidate this. `@etyma/core`/`angular`/`analog`
0.6.0 only added definition-first key utility types (`I18nMessageKey`,
`I18nKeysRequiringParams`, `I18nKeysWithoutRequiredParams`, `I18nMessageArgs`) - types only,
no runtime, contract or `t()` change. Every `@etyma/tooling` and `@etyma/cli` release since
(source analysis for JS/TS, Angular templates and Astro files, project-local wrapper
provenance, unknown-key suggestions) is an additive developer-tooling capability over
application source; none replaces the runtime architecture the consumers use, and neither
consumer is required to adopt them.

## Internal dogfood

The two applications in this repository deliberately author their source catalogs
differently, so both documented workflows run in CI against the current API:

- **`apps/www` - JSON + contract.** `en.json` is the whole source catalog;
  `src/app/i18n/etyma.generated.ts` is generated by the public `etyma contract` binary and
  committed. `pnpm check` and the CI workflow run `etyma contract --check` after the
  packages build, so a stale contract fails the build. Its `typecheck` also runs `ngc` over
  `tsconfig.app.json`, so `t('footer.rights', { year })` (`:number`) and
  `t('button.released', { on })` (`:date`) are type-checked in real templates, and
  `src/app/i18n/inject.types.ts` asserts the rejections.
- **`apps/playground` - JSON + `defineMessages()`.** No generated local contract: it is the
  proof that typed keys need no generation step.

## Explicitly post-1.0

None of these blocks 1.0, and none of them requires changing an API that 1.0 freezes:

- Source analysis is implemented before 1.0: the JS/TS engine in `@etyma/tooling/source`, the
  filesystem CLI adapter, opt-in Angular template and Astro `.astro` analysis, and conservative
  project-local relative wrapper provenance. Still future: general dataflow, `tsconfig`/Vite
  alias resolution, richer re-export/module graphs, source-message extraction and hardcoded-copy
  detection - all additive capabilities over application source, not changes to the catalog,
  contract or runtime model. None of it, the shipped part included, is a 1.0 blocker.
- React, Vue and Svelte adapters - additive, built on the advanced core API that
  `@etyma/angular` and `@etyma/astro` already use.
- `etyma.config.ts` or any project configuration file.
- An MCP server, CMS integrations, authenticated remote providers.
- `etyma pull`/`push`/`sync`, a translation UI, automatic translation.
- An Astro integration plugin.
